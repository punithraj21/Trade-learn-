# Trade Learn

An online reading app for the "Learn Stock Trading — From Zero to Confident" course
(8 modules, 60 chapters, 114-term glossary). Content-driven Next.js app: every
chapter is a static page generated from Markdown files under `docs/`.

## Tech stack

- **Next.js 16** (App Router, Turbopack)
- **React 19**
- **Tailwind CSS 3** + `@tailwindcss/typography`
- **TypeScript**
- **gray-matter** (chapter YAML frontmatter, build time only) + **react-markdown** / **remark-gfm** (chapter body rendering)
- **@opennextjs/cloudflare** + **wrangler** — deploys as a Cloudflare Worker (`npm run deploy`)
- No database, no API routes, no env vars — fully static content, generated at build time via `generateStaticParams`.

## Routes

| Path | Purpose |
| --- | --- |
| `/` | Course home — hero, disclaimer, overall progress bar, module grid |
| `/modules/[moduleId]` | Chapter list for one module (8 total: `foundations`, `price-action`, `market-structure`, `indicators`, `fundamentals`, `strategies`, `risk-psychology`, `mastery`) |
| `/chapters/[slug]` | Chapter reader — full Markdown body, on-page outline, mark-complete toggle, prev/next nav (flows across module boundaries) |
| `/glossary` | All glossary terms, alphabetically grouped, with client-side search |

## File layout

- `docs/` — **all course content**, copied verbatim from `punithraj21/forever`'s `claude/stock-trading-docs-eedepw` branch (that branch's own commits name this repo as the intended publish target). Don't hand-edit content here without also checking whether `forever`'s branch should be updated to match — it's the canonical source the content pipeline wrote to.
  - `docs/manifest.json` — the whole curriculum as data: `course` metadata + `modules[]`, each with `chapters[]` (`id`, `order`, `slug`, `file`, `title`, `difficulty`, `estimated_minutes`, `tags`, `prerequisites`, `summary`). This is the single source of truth for navigation — `lib/course.ts` never hardcodes a chapter list.
  - `docs/chapters/NN-module/NN-slug.md` — one chapter per file, `NN` = global chapter id so files sort in reading order. YAML frontmatter (id, module, module_title, order, title, slug, difficulty, estimated_minutes, tags, prerequisites, summary) + a body using fixed `## <emoji> Heading` sections (see `docs/STYLE_GUIDE.md`): 🎯 What you'll learn, 📘 Key concepts, 🔍 Example, ⚠️ Common mistakes, ✅ Key takeaways, 📝 Quick check, 📖 New words.
  - `docs/reference/glossary.md` — frontmatter + `## <Letter>` sections of `- **Term** — definition` lines.
- `scripts/generate-content.mjs` — **build-time only.** Reads `docs/manifest.json` + every chapter's Markdown (via `gray-matter`) + `docs/reference/glossary.md`, and writes it all into `lib/generated/content.json`. Runs automatically via the `predev`/`prebuild` npm hooks. **This exists because of a real production bug, not style preference:** `lib/course.ts`/`lib/glossary.ts` originally called `fs.readFileSync(path.join(process.cwd(), "docs", ...))` at request time — that works under `next start` but 500s under the Cloudflare Workers runtime (`ENOENT: /bundle/docs/manifest.json`), because the Worker's request-time sandbox doesn't carry `docs/` into its bundle the way a traced/imported file does. Importing a generated JSON file instead bakes the content into the JS bundle at build time, so it works identically under Node, edge, and Workers. **Don't revert `lib/course.ts`/`lib/glossary.ts` to runtime `fs` reads of `docs/`** — confirmed broken via `wrangler dev --local` against the real Workers runtime, fixed the same way, re-verified.
- `lib/generated/content.json` — generated, but **committed** (not gitignored) so it's always present regardless of which tool invokes the build (some CI paths call `next build` directly rather than `npm run build`, which would skip an npm `prebuild` hook). Regenerate with `npm run generate:content` after editing anything under `docs/`, or just run `npm run dev`/`npm run build` (the hooks do it for you) and commit the result alongside your `docs/` change.
- `lib/course.ts` — imports `lib/generated/content.json` (no `fs`/`path` at runtime). Exposes `getManifest`, `getModules`, `getModule`, `getAllChapterMetas` (flattened, sorted by `id`), `getChapterBySlug`, `getAdjacentChapters` (prev/next across the whole 60-chapter sequence, not just within a module).
- `lib/glossary.ts` — imports the same generated JSON's `glossary` field (parsed at build time by `scripts/generate-content.mjs` via regex-matching `## <Letter>` headers and `- **Term** — definition` lines against `docs/reference/glossary.md`). If the glossary's dash style or heading format ever changes, update the parser in `scripts/generate-content.mjs`, not `lib/glossary.ts`.
- `lib/slug.ts` — `slugify()` strips emoji + normalizes text into a heading id. **Must stay in sync** between `components/ChapterMarkdown.tsx` (assigns `id={slugify(headingText)}` on every rendered `h2`) and `lib/course.ts`'s `extractOutline()` (builds the "on this page" sidebar links from the same headings) — they don't share a single call site, so a change to one needs the matching change in the other, or outline links will 404-anchor.
- `lib/useProgress.ts` — client-only progress tracking via `localStorage` (key `trade-learn:progress:v1`, a JSON array of completed chapter ids), read through `useSyncExternalStore` so multiple components (Header badge, module chapter checkmarks, chapter mark-complete button) stay in sync within a tab, and a `storage` event listener syncs across tabs. No backend — progress is per-browser, never sent anywhere.
- `components/ChapterMarkdown.tsx` — server component rendering a chapter body via `react-markdown` + `remark-gfm`. Custom renderers: `h2` (assigns the slugified id), `blockquote` (styled as an indigo callout box — used for the "> In one line:" summary every chapter opens with), `code` (distinguishes inline vs fenced by presence of a `className`, since `react-markdown` only sets `className` on fenced code blocks). `img`/`p` work together to render a standalone `![alt](src)` line (every chapter diagram) as a `<figure><img/><figcaption/></figure>` — **`img` must stay a plain `<img>`, never a `<figure>` itself**: a bare `![...]()` line is a paragraph containing only an image per CommonMark, so `figure` (a block element) inside a `<p>` is invalid HTML that the browser silently re-nests, which then mismatches React's hydration and blows away the whole tree client-side (hit this for real — every one of the 316 chapter diagrams triggered it before the fix). `p`'s override detects "this paragraph's only child is one of ours" by checking `child.type === ChapterImage` (**referential equality against the hoisted component function, not the string `"img"`** — react-markdown passes the component override itself as the unrendered child's `.type`, since children are element descriptors until React actually reconciles them) and renders the figure directly with no `<p>` wrapper in that case.
- `scripts/generate-diagrams.mjs` — content-authoring tool (not imported by the app) exposing 8 pure SVG-generator functions (`priceLine`, `candlestick`, `candleAnatomy`, `indicatorPanel`, `barCompare`, `riskReward`, `donut`, `flow`) via a CLI: `node scripts/generate-diagrams.mjs <output.svg> --spec-file <spec.json>` (or an inline JSON arg — but titles/labels with apostrophes break shell quoting, so prefer `--spec-file`). Palette validated with the dataviz skill's `validate_palette.js` against the light chart surface: accent lines `#2a78d6`/`#eb6834` pass CVD+contrast as a pair; up/down `#0ca30c`/`#d03b3b` fail bare-hue CVD separation (the classic red/green problem), so every up/down encoding also carries a shape/position cue — candle bodies are hollow (outline) when up, solid-filled when down; gain/loss bars are told apart by which side of a drawn zero-baseline they sit on. These are static illustrative figures (served as `.svg` files via plain `<img>`, not live interactive DOM charts), so there's no hover/tooltip layer.
- `public/diagrams/*.svg` — generated diagram files, one set per chapter (`<slug>-1.svg`, `-2.svg`, ...), referenced from the corresponding chapter's Markdown via `![alt](/diagrams/<file>.svg)`. Committed (not gitignored) — they're content, not build output.
- `components/ChapterActions.tsx` — client component: mark-complete toggle + prev/next chapter links.
- `components/{Header,OverallProgress,ModuleGrid,ChapterListItem,GlossarySearch}.tsx` — all client components that read `useProgress()` (or, for `GlossarySearch`, local `useState` filtering); everything else in `app/` is a server component.

## Content authoring

To add or edit a chapter: follow `docs/STYLE_GUIDE.md`'s frontmatter + section-heading contract exactly — `lib/course.ts` and `components/ChapterMarkdown.tsx` assume every chapter uses the same fixed `## <emoji> Heading` set for the on-page outline to make sense, and the manifest's `id`/`order`/`slug`/`file` fields must match the file's own frontmatter or `getAllChapterMetas()`/`getAdjacentChapters()` will disagree with what's on disk.

## Build / deploy

- `npm run dev` — local dev on port 3000 (regenerates `lib/generated/content.json` first via `predev`)
- `npm run build` — production build; all 60 chapter pages + 8 module pages + home + glossary are statically generated (`generateStaticParams`); regenerates content first via `prebuild`
- `npm run deploy` — `opennextjs-cloudflare build && opennextjs-cloudflare deploy`, ships to Cloudflare Workers. Needs `wrangler` authenticated (`npx wrangler login`, or `CLOUDFLARE_API_TOKEN`+`CLOUDFLARE_ACCOUNT_ID` in CI) — nothing in this repo provides that.
- `npm run preview` — same build, but `opennextjs-cloudflare preview` (runs it locally against the real Workers runtime via `wrangler dev`, no deploy)
- `wrangler.jsonc` — no bindings, no custom domain, deploys to `trade-learn.<subdomain>.workers.dev` by default. Add a `routes` entry for a custom domain (see `punithraj21/forever`'s `wrangler.jsonc` for the pattern). Currently live at a custom domain (`trade.devshark.site`) configured directly in the Cloudflare dashboard rather than in this file.
- **Cloudflare Workers Builds (the dashboard's Git integration) has its own Build/Deploy command fields — get this wrong and it fails silently.** The Worker's `main` (per `wrangler.jsonc`) is `.open-next/worker.js`, which only `opennextjs-cloudflare build` produces; plain `next build` (i.e. `npm run build`) does not. If the dashboard's **Build command** is set to `npm run build` instead of **`npx opennextjs-cloudflare build`**, every push-triggered build fails at the `wrangler deploy` step ("entry-point file `.open-next/worker.js` was not found") — and a failed build produces **no new entry in the Deployments tab at all**, so the site keeps silently serving whatever deployed last, with no obvious signal that new commits aren't landing. Hit this for real: pushed several rounds of real changes that never appeared live, with Deployments still showing only pre-existing entries from before Git was even connected. Correct settings: Build command `npx opennextjs-cloudflare build`, Deploy command `npx wrangler deploy`, root directory `/`. Check failures in the **Builds** tab (separate from **Deployments**, which only lists successes) — a build's own log shows the actual error.
- No environment variables required — see `.env.example`
- Also deploys as a plain Next.js app to Vercel or any Next.js-compatible host; no config beyond the default framework preset (the `docs/`-at-request-time bug this repo hit is Workers-specific — Vercel's Node runtime doesn't have that sandbox restriction — but the generated-JSON approach works everywhere, so there's no reason to special-case it)
